Built for CalHacks 13.0 solo, and won Honorable Mention in the SpacetimeDB track out of 150+ projects.

I built Geonosis because I see first hand how difficult deploying a robot is at Northstar Robotics.

For any frontier model such as π0.5, and even world models, robots require clean demonstrations in order to perform any task with at least some reliability.

However getting data either requires VC money to pay 600k+ for data, or you set up your own data collection infrastructure. Then you still need to figure out how to train your models, and it's not as simple as just throwing data at π0.5. What data to collect, and how you collect it, is vitally important. This creates a huge barrier to entry for most people deploying robots.

I built Geonosis AI to be the robot deployment factory. From any embodiment and task, you get a fleet of agents that run the entire deployment pipeline: collecting data by outsourcing operators, running evals on a physical robot, training, and shipping the checkpoint.

## How it works

You file a ticket: "Pick up the cube and place it on the plate, 75% reliable, $50 budget." The ticket then moves down a line of agent stations, like a part moving through a factory.

<Figure src="/projects/geonosis-ai/01-landing.jpg" caption="The landing page, with live numbers straight from SpacetimeDB." alt="The GeonosisAI landing page: the tagline Ticket in. Deployed robot out., an isometric drawing of a factory floor, and live counters for robots online, open paid tasks and tickets shipped" ratio="wide" />

1. **Baseline.** The robot runs the task on its current policy. Every trial is recorded with its outcome.
2. **Diagnose.** Claude groups the failed trials by why they failed, from trial notes, timings and camera frames.
3. **Plan data.** The planner reads the failure clusters, the success rate and the budget, and decides what data fixes them: recovery takeovers (the robot pauses mid-failure and a person takes over) or clean demos, and how many. Its reasoning has to quote a failure cluster, and a human approves the spend.
4. **Collect.** Paid tasks go out as job drops on Discord and as texts ("Reply YES to claim"). A contributor claims the task on their phone, sees the robot's cameras, drives the arm from the browser and hands control back. In the demo the robot sat behind a Cloudflare tunnel, so anyone who got the text could tunnel in and give a demonstration.
5. **Review.** Deterministic checks (timestamps, jerk, dropped frames, length) plus a Claude vision review. Rejected episodes show why. Accepted ones get paid (Stripe test mode).
6. **Train.** A π0.5 LoRA fine-tune on an H100 on Modal, from the accepted episodes converted to LeRobot format.
7. **Eval and ship.** The new checkpoint runs the same eval. If it clears the target it ships with a report. If not, the line loops back and buys more data.

The eval agent is also what decides what data is needed. If the robot is failing in a specific way, it probably needs recovery data for that failure, not more generic clean demos.

## Agents that sleep on the database

Under the hood we use Factory Droids plus the Claude API to make a swarm of agents, each with its own role. SpacetimeDB is the real-time database that decides when each of them gets kicked off.

Every service, agent, robot and phone reads and writes the same SpacetimeDB tables. The orchestrator, three kinds of Factory Droids, the Jetson, the MuJoCo sim, the web app and every contributor's phone all share 23 tables, and the only way to change them is through about 55 reducers. The safety rules live inside those reducers, not in prompts:

- one arm-control lease per robot, so two phones can never drive the same arm,
- no payout can exceed the human-approved budget,
- a droid can only point training at a dataset where every episode was accepted by review,
- the event log can only be appended to, never edited, and carries a chain hash.

The part I like most is how the agents wait. A droid ends its turn with one line:

```text
WAITING_FOR dataset:accepted_count>=5
```

and goes idle for free. No process is held open. A resume bridge in the orchestrator re-checks that predicate on every row change, and when it turns true it wakes the same Factory session with what changed. In testing, an accepted review woke a parked Data Droid in 597 ms.

<Figure src="/projects/geonosis-ai/09-factory-droids.jpg" caption="A Training Droid parked on a training run, and the Data Droid that SpacetimeDB just woke up." alt="The Agents page: a Training Droid session log ending in a WAITING_FOR predicate on training run 7, a Data Droid tagged Just woken by SpacetimeDB, and the planner's verbatim reasoning for buying one clean demo next to the human's $10 approval" ratio="wide" />

Three droids do the work a robotics engineer would otherwise do between steps. The Onboarding Droid sets up a new robot's adapter and safety checks. The Data Droid validates the accepted episodes, cuts the failure frames before each takeover and assembles the LeRobot dataset. The Training Droid sanity-checks the data before any GPU is spent, picks hyperparameters, queues the H100 run and sleeps. If the run hits an OOM, it wakes, halves the batch and retries once.

<Figure src="/projects/geonosis-ai/08-agent-factory-floor.jpg" caption="The factory cell for one ticket, and the decision trail: what failed, what we bought, and why, each step linked by row id." alt="The Agents page for a simulated ticket: an isometric factory cell with the dispatcher at the collect dock, and a decision trail listing the failed trials, the failure cluster Claude found and the data plan, each with its event id" ratio="wide" />

Everything a droid does lands as an event, so the factory floor shows droids riding to their station, sleeping with their predicate on screen, and waking when the database wakes them.

## The robot side

The robot client runs on an NVIDIA Jetson next to the real I2RT YAM, and the same code runs a MuJoCo model of the same arm. One adapter interface, one safety layer in front of every command: joint limits, velocity and acceleration caps, a workspace box, a watchdog and a soft e-stop. Sim and real numbers are never pooled.

Inference is remote. The policy server on Modal hot-swaps checkpoints, and the round trip is about 157 ms, which is several control steps. The robot runs 50-step action chunks asynchronously and crossfades between them to hide it.

## Hurdles

- **No arm overnight.** Nobody could be next to the YAM all night, so I built a physics sim of the same arm behind the same adapter and safety layer, and made sim or real a fact on every row.
- **Droids that have to wait for hours.** Agents normally run and finish. I needed them to park on a database condition and come back later with full context, so I built the wait-for protocol and resume bridge myself.
- **Remote inference at control rate.** A 157 ms round trip is several control steps. Async action chunks, dropping the stale prefix and crossfading made it smooth.
- **A real arm is not a sim.** Gravity pulls joints off their targets, the Jetson's ffmpeg has no H.264 encoder, and the arm has to fold back to rest safely after every trial. Each one cost hours.

<Figure src="/projects/geonosis-ai/07-finetuned-eval-real-arm.jpg" caption="The real arm at 6 in the morning. Trial 1 of the fine-tuned eval never moved because the websocket to the policy server dropped." alt="The fine-tuned eval on the real arm: trial 1 failed before moving because the connection to the policy server closed with a protocol error, and trial 2 is running with the arm visible on the top camera" ratio="wide" />

- **Ten trials is a small sample.** A strict confidence-interval rule can never certify 80% from 10 trials, so the factory ships on the point estimate and always shows the interval.
- **Many agents, one repo.** I built this with a team of coding agents working off one shared task board, and agents with stale git state reverted each other's work more than once. A pre-commit hook now refuses silent deletions.

## What I learned

- The hard part of "AI deploys your robot" isn't the model. It's the plumbing that touches the physical world: who resets the cube, who takes over when it drops, how a GPU job wakes an agent, how a payout waits on a review.
- Agents need to be able to sleep. A session parked on a database condition costs nothing and comes back with full context. That turns a coding agent into a long-running worker.
- Guardrails belong in code, not prompts. The planner must cite a failure, a payout can't exceed the approved budget, the event log can't be rewritten.
- A sim is only useful if nobody can mistake it for the real thing.
